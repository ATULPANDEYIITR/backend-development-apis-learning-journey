# Idempotency Engineering: Idempotent APIs, Duplicate Requests and Payment Workflows

## 1. Technical Scope

Idempotency is a distributed application design property that allows a system to process repeated requests without unintentionally repeating their business effects.

It is particularly important in payment APIs, financial transactions, order creation, subscription management, inventory allocation and other operations where duplicate execution can produce inconsistent or costly outcomes.

A client may submit a payment request and fail to receive its response because of:

- Network interruption.
- Gateway timeout.
- Client-side connection failure.
- Load balancer interruption.
- Application restart.
- Delayed processing.
- Response delivery failure.

The absence of a response does not establish that the operation failed.

A payment may have succeeded even when the client received a timeout.

Idempotency addresses this uncertainty by associating repeated requests with a stable operation identity and preserving the original result.

The implementations demonstrate four complementary engineering perspectives:

| Implementation | Primary engineering perspective |
|---|---|
| Python | Payment workflow simulation and request validation |
| JavaScript | Asynchronous execution and concurrent request coordination |
| C++17 | Repository-independent governance engine for payment state and reconciliation |
| Java 17 | Enterprise domain modeling and policy-driven transaction management |
| PostgreSQL | Persistent idempotency registry, transaction integrity and operational reporting |

## 2. Core Concepts

### 2.1 Idempotent Operation

An operation is idempotent when repeating the same operation produces the same intended business result as executing it once.

For an operation \(f\):

\[
f(f(x)) = f(x)
\]

This describes the desired behavior of repeated execution.

For an HTTP API, the response to a retry does not necessarily need to be identical in every transport-level detail. The important requirement is that the business operation is not performed again.

For example:

A customer submits a payment of INR 250.

The payment provider processes the charge, but the HTTP response is lost.

The customer retries using the original idempotency key.

The API retrieves the original payment result rather than creating another charge.

### 2.2 Idempotent API

An idempotent API is designed to handle repeated requests safely.

HTTP methods such as PUT and DELETE have defined idempotent semantics, while POST is not inherently idempotent.

A payment creation endpoint commonly uses POST with an application-level idempotency mechanism.

Example endpoint:

`POST /api/v1/payments`

Request headers:

| Header | Purpose |
|---|---|
| `Content-Type` | Specifies JSON request content |
| `Idempotency-Key` | Identifies the logical operation |
| `Authorization` | Authenticates the caller |

The API must associate the key with the authenticated customer or account and validate the request before processing it.

An idempotency key does not replace authentication, authorization or transaction integrity.

### 2.3 Idempotency Key

An idempotency key is a unique identifier generated by the client for one logical operation.

Example:

`payment_request_500001`

The same key must be reused when retrying the same logical payment.

A new key represents a different logical operation.

A suitable key should:

- Have sufficient randomness or uniqueness.
- Be difficult to guess.
- Remain unchanged across retries.
- Be scoped to an authenticated customer or tenant.
- Have a documented retention period.
- Avoid containing confidential information.

The implementations validate key length and permitted characters.

Production systems should also consider rate limits and abuse prevention.

### 2.4 Request Fingerprint

A key alone cannot establish that two requests represent the same operation.

The system must compare the business parameters associated with the original request and the retry.

A request fingerprint is calculated from a canonical representation of relevant request fields.

For example:

\[
F = SHA256(CanonicalRequest)
\]

A payment fingerprint may include:

- Customer identifier.
- Amount in minor currency units.
- Currency.
- Payment method token reference.

The following requests must not be treated as identical:

| Request | Amount | Key | Decision |
|---|---:|---|---|
| Original | INR 250 | Same | Create |
| Retry | INR 250 | Same | Replay |
| Modified | INR 500 | Same | Reject |
| New payment | INR 500 | New | Create separately |

The canonical representation must be deterministic.

Field ordering, numeric representation, omitted values and normalization rules must be consistent.

Sensitive payment credentials must never be stored in plaintext merely to calculate a fingerprint.

A cryptographic hash identifies matching request content. It does not encrypt that content.

## 3. Duplicate Request Processing

### 3.1 Request Lifecycle

The normal request lifecycle is:

Client request  
→ Authentication  
→ Input validation  
→ Idempotency key validation  
→ Request fingerprint calculation  
→ Key lookup  
→ Duplicate detection  
→ Key reservation  
→ Payment creation  
→ Provider execution  
→ State persistence  
→ Response caching  
→ Client response

A retry follows a different path:

Client retry  
→ Authentication  
→ Input validation  
→ Fingerprint calculation  
→ Existing key lookup  
→ Fingerprint comparison  
→ State evaluation  
→ Original response retrieval

The retry must not independently execute the payment operation.

### 3.2 Idempotency Decision Table

| Existing key | Fingerprint | Stored state | Action |
|---|---|---|---|
| No | New | None | Reserve and execute |
| Yes | Same | PROCESSING | Return pending or coordinate with original request |
| Yes | Same | SUCCEEDED | Replay successful result |
| Yes | Same | FAILED | Replay stored failure according to policy |
| Yes | Different | Any | Reject with conflict |
| Yes | Same | UNKNOWN | Reconcile provider outcome |
| Yes | Same | Expired | Apply documented expiration and reconciliation policy |

The system must distinguish duplicate detection from duplicate execution.

A duplicate request is not necessarily a failed request. It may be a valid retry of an operation that already succeeded.

### 3.3 Response Caching

A completed idempotency record stores sufficient information to reproduce the original API result.

Typical stored attributes include:

- HTTP status code.
- Payment identifier.
- Business result.
- Error code.
- Relevant response metadata.
- Request fingerprint.
- Creation time.
- Expiration time.

The cached response must not expose confidential provider credentials, authentication tokens or unnecessary personal information.

The Python, JavaScript and Java implementations preserve the original payment identifier and result.

The PostgreSQL implementation stores the response in a JSONB column.

## 4. Payment State Management

### 4.1 Payment States

The implementations use four principal states.

| State | Meaning | Retry behavior |
|---|---|---|
| PROCESSING | Payment execution has started | Coordinate with original operation |
| SUCCEEDED | Provider confirmed successful payment | Return original success |
| FAILED | Failure is confirmed | Return recorded failure |
| UNKNOWN | Provider outcome cannot yet be established | Reconcile before another charge |

These states represent business execution, not simply HTTP response delivery.

### 4.2 Valid State Transitions

The supported transition model is:

PROCESSING  
├── SUCCEEDED  
├── FAILED  
└── UNKNOWN  

UNKNOWN  
├── SUCCEEDED  
└── FAILED  

SUCCEEDED and FAILED are terminal states in the implemented model.

The transition from UNKNOWN is permitted because the payment provider may later confirm whether the original operation succeeded.

An UNKNOWN state must not automatically become FAILED merely because a network request timed out.

### 4.3 Why UNKNOWN Matters

Consider the following sequence:

1. The payment service sends a charge request.
2. The provider processes the charge.
3. The provider sends a successful response.
4. The network connection fails before the application receives that response.
5. The application cannot establish whether the payment succeeded.

Repeating the charge without checking the provider could create a second payment.

The correct workflow is:

- Preserve the original operation identifier.
- Mark the outcome as UNKNOWN.
- Query the provider using its transaction reference or supported lookup mechanism.
- Reconcile the original operation.
- Update the payment and idempotency records.
- Return the confirmed result on subsequent retries.

This is an important distinction between confirmed failure and uncertain execution.

## 5. Python Implementation

The Python implementation provides an object-oriented simulation of an idempotent payment service.

### 5.1 Domain Structures

The main components are:

| Component | Responsibility |
|---|---|
| `PaymentRequest` | Validates and fingerprints payment input |
| `Payment` | Represents payment execution |
| `IdempotencyRecord` | Stores key, fingerprint and cached result |
| `PaymentProcessor` | Coordinates request processing |
| `PaymentStatus` | Defines payment lifecycle states |

Dataclasses provide structured domain objects.

Enums prevent arbitrary status strings from being used throughout the workflow.

### 5.2 Request Processing

The `create_payment()` method performs the following operations:

1. Validates the idempotency key.
2. Validates the payment request.
3. Calculates a SHA-256 fingerprint.
4. Checks for an existing record.
5. Rejects conflicting payloads.
6. Returns a cached result for completed requests.
7. Reserves a new key.
8. Creates the payment.
9. Executes the simulated gateway operation.
10. Stores the result.

The use of `threading.RLock` protects the in-memory registry and payment state from simultaneous modifications.

### 5.3 Failure Handling

The implementation demonstrates:

- Invalid key rejection.
- Invalid amount rejection.
- Duplicate request handling.
- Request fingerprint conflicts.
- Gateway-declined payments.
- Cached failure responses.
- Expiration handling.
- Event recording.

The event log uses hashed key identifiers rather than printing the original idempotency keys.

### 5.4 Testing

The executable assertions verify:

- Initial payment creation.
- Successful duplicate replay.
- Stable payment identifiers.
- Rejection of modified request parameters.
- Failure result caching.
- Input validation.

The in-memory locking strategy is suitable for simulation but does not provide distributed coordination across multiple application instances.

A production implementation requires persistent atomic reservations.

## 6. JavaScript Implementation

The JavaScript implementation focuses on asynchronous payment processing and event-driven behavior.

### 6.1 Event-Driven Architecture

The `IdempotencyService` extends Node.js `EventEmitter`.

It produces events for:

- Payment processing.
- Payment success.
- Payment failure.
- Duplicate request detection.

This separates operational notifications from the core payment workflow.

Monitoring systems can use such events to track payment processing and failure patterns.

### 6.2 Promise-Based Duplicate Coordination

The implementation stores a Promise in the idempotency record when a new operation starts.

If another request arrives with the same key while the original operation is running, it awaits the existing Promise.

The sequence is:

Request A  
→ Reserve key  
→ Start provider operation  
→ Store Promise  

Request B  
→ Find existing key  
→ Validate fingerprint  
→ Await existing Promise  

Both requests receive the result associated with the same payment.

The reservation occurs before the first asynchronous operation, preventing another event-loop task from inserting a competing operation between lookup and reservation.

### 6.3 Maps and Event Handling

JavaScript `Map` structures provide average constant-time lookup for:

- Idempotency records.
- Payment records.

The event emitter provides a lightweight mechanism for operational observability.

The implementation also uses Node.js cryptographic functions for UUID generation and SHA-256 fingerprinting.

### 6.4 Important Limitation

An in-memory Promise is shared only inside one Node.js process.

If multiple application servers receive requests with the same key, their Maps are independent.

Distributed idempotency therefore requires shared persistent storage, such as PostgreSQL, and atomic database operations.

The JavaScript implementation should be understood as a concurrency model rather than a complete distributed payment infrastructure.

## 7. C++17 Implementation

The C++ implementation models payment governance through explicit state management and controlled reconciliation.

### 7.1 Domain Model

The main structures are:

| Structure | Purpose |
|---|---|
| `PaymentRequest` | Validated payment parameters |
| `Payment` | Business transaction state |
| `IdempotencyRecord` | Request identity and expiration |
| `OperationResult` | Processing decision and response |
| `PaymentGateway` | Simulated provider |
| `GovernanceEngine` | Coordinates payment governance |

### 7.2 Governance Decisions

The engine distinguishes three request outcomes:

- CREATED: A new payment operation was reserved and executed.
- REPLAYED: A previous completed operation was returned.
- IN_PROGRESS: The original operation requires completion or reconciliation.

A conflicting fingerprint produces an exception.

This makes the decision process explicit rather than relying on implicit response handling.

### 7.3 Uncertain Payment Outcomes

The `simulateUnknown()` method demonstrates a payment whose execution outcome is uncertain.

The `reconcile()` method accepts a confirmed provider decision.

If the provider confirms success, the payment transitions to SUCCEEDED.

If the provider confirms that no charge occurred, the payment transitions to FAILED.

The engine does not automatically execute a second charge.

### 7.4 Data Structure Selection

The implementation uses:

- `unordered_map` for average constant-time key and payment lookup.
- `vector` for ordered audit events.
- `map` for deterministic reporting.
- `enum class` for type-safe status definitions.

The request fingerprint uses a demonstration standard-library hash.

Unlike SHA-256, `std::hash` is not a suitable cryptographic fingerprint for production idempotency. A production implementation should use a cryptographic library and a stable canonical serialization format.

The engine is intentionally single-threaded. A production multithreaded implementation would require synchronized registries, atomic persistence and safe provider coordination.

## 8. Java 17 Enterprise Implementation

The Java implementation emphasizes explicit domain boundaries, policy objects and enterprise service responsibilities.

### 8.1 Immutable Request Modeling

The `PaymentRequest` record provides an immutable representation of payment input.

Construction-time validation prevents invalid requests from entering the service layer.

The fingerprint is calculated from selected business attributes.

Java 17 records reduce unnecessary mutable state and make request objects easier to validate and pass between services.

### 8.2 Policy-Based Design

`IdempotencyPolicy` defines:

- Key retention.
- Whether failures are cached.
- Whether request fingerprint validation is mandatory.

The policy object separates operational configuration from payment processing logic.

The default policy uses a 24-hour retention period.

### 8.3 Per-Key Concurrency Control

The Java implementation uses:

- `ConcurrentHashMap` for shared registries.
- `ReentrantLock` for per-key synchronization.
- Immutable request records.
- Explicit payment transitions.
- A provider interface.

A per-key lock prevents simultaneous processing of the same operation while allowing unrelated payments to proceed independently.

The provider interface separates payment execution from business policy.

### 8.4 State Transition Enforcement

The `Payment.transition()` method validates state changes.

For example:

- PROCESSING to SUCCEEDED is allowed.
- PROCESSING to FAILED is allowed.
- PROCESSING to UNKNOWN is allowed.
- UNKNOWN to SUCCEEDED is allowed.
- UNKNOWN to FAILED is allowed.
- SUCCEEDED to FAILED is rejected.

This prevents invalid business transitions from being introduced by unrelated service methods.

### 8.5 Enterprise Considerations

The implementation includes:

- Custom domain exceptions.
- Immutable request structures.
- Policy validation.
- Payment-provider abstraction.
- Audit event collection.
- Concurrent request coordination.
- Reconciliation.
- Operational aggregation.
- Expiration cleanup.

The implementation uses local locks and in-memory records. Production deployments should replace these with distributed persistence and carefully defined transaction boundaries.

## 9. PostgreSQL Implementation

PostgreSQL provides the persistent coordination layer required by a distributed idempotent API.

Unlike process-local data structures, database constraints and transactions coordinate requests across application instances.

### 9.1 Relational Architecture

The database contains the following entities:

| Table | Responsibility |
|---|---|
| `customers` | Customer identity |
| `payment_methods` | Tokenized payment method references |
| `payments` | Payment business transactions |
| `idempotency_keys` | Request identity and cached results |
| `gateway_attempts` | Provider execution history |
| `api_events` | Operational audit trail |

The relationship is:

Customer  
→ Payment Methods  
→ Payments  
→ Gateway Attempts  

Customer  
→ Idempotency Keys  
→ Payment  

Payment  
→ API Events  

The payment and idempotency records are linked through the payment identifier.

### 9.2 Unique Constraint Enforcement

The `idempotency_keys` table defines:

`UNIQUE (idempotency_key)`

This prevents two independent transactions from successfully registering the same key.

The `register_idempotency_request()` function uses `INSERT ... ON CONFLICT DO NOTHING`.

A competing request then retrieves and locks the existing record using `SELECT ... FOR UPDATE`.

The fingerprint is compared before the function returns the original operation state.

This is more reliable than checking for an existing key and inserting a new record in two unrelated transactions.

### 9.3 Transactional Processing

The recommended application transaction is:

BEGIN  
→ Register idempotency key  
→ Create payment  
→ Associate payment with key  
→ Persist provider outcome  
→ Update cached response  
→ COMMIT  

The sample SQL demonstrates this sequence inside transactional `DO` blocks.

A database transaction guarantees atomicity for database operations.

It does not automatically make an external payment provider part of the same transaction.

The external provider operation therefore requires a separate coordination strategy.

### 9.4 Row-Level Locking

`SELECT ... FOR UPDATE` locks the selected idempotency and payment records until the transaction completes.

This prevents concurrent transactions from independently modifying the same record.

`FOR UPDATE SKIP LOCKED` is used during batch expiration cleanup to avoid workers selecting records already locked by other cleanup workers.

### 9.5 Database State Enforcement

The `validate_payment_transition()` trigger restricts payment state changes.

It permits the intended transitions and rejects invalid transitions.

The audit trigger creates operational events when payment states change.

Database-level enforcement is valuable because it protects integrity even when several application services interact with the same tables.

### 9.6 Gateway Attempt History

The `gateway_attempts` table maintains provider execution information.

Each attempt has a unique combination of:

- Payment identifier.
- Attempt number.

The history helps distinguish an original provider execution from a later reconciliation operation.

Provider references are retained when available.

This supports operational investigation and prevents the payment table from becoming the only source of execution history.

### 9.7 Reconciliation Function

`reconcile_payment()` handles payments in PROCESSING or UNKNOWN states.

It requires an authoritative provider decision.

A confirmed provider success updates the payment and idempotency record to successful states.

A confirmed absence of a charge updates them to failed states.

The function also records the reconciliation attempt and audit event.

### 9.8 Retention and Cleanup

Idempotency keys should not be retained indefinitely without an operational reason.

The sample uses a 24-hour default retention period.

The cleanup function removes expired terminal records in controlled batches.

PROCESSING and UNKNOWN records are excluded.

This prevents unresolved transactions from losing their protection merely because a timer expired.

Retention must be aligned with client retry windows, provider reconciliation periods, business requirements and financial recordkeeping obligations.

## 10. Idempotency Versus Exactly-Once Processing

Idempotency and exactly-once execution are related but different concepts.

| Concept | Meaning |
|---|---|
| At-most-once business effect | Repeated requests do not create repeated effects |
| At-least-once delivery | A message or request may be delivered multiple times |
| Idempotent processing | Repeated processing produces the same intended business outcome |
| Exactly-once processing | A stronger end-to-end guarantee requiring coordination across execution and persistence boundaries |

In distributed systems, a client cannot reliably determine whether an operation failed simply because its response was lost.

An idempotency key provides a stable operation identity.

A durable record provides evidence of processing.

A provider reference supports reconciliation.

Together, these mechanisms can achieve effectively-once business behavior for a defined operation and retention period.

They do not establish universal exactly-once execution across independent systems.

## 11. Idempotency Versus Database Transactions

Database transactions and idempotency solve different problems.

| Property | Database transaction | Idempotency |
|---|---|---|
| Primary objective | Atomic database changes | Safe repeated operations |
| Scope | Transactional database resources | Logical request identity |
| Duplicate prevention | Not guaranteed automatically | Explicitly managed |
| Rollback | Supports rollback | Does not reverse an external operation |
| Retry handling | Application-controlled | Returns or coordinates original result |
| External gateway | Not automatically included | Requires provider reconciliation |

A payment system needs both.

A transaction ensures that the payment and its idempotency record remain consistent within the database.

The idempotency mechanism ensures that a repeated client request does not create another logical payment.

## 12. Security Considerations

### 12.1 Authentication and Authorization

The caller must be authenticated before the payment request is processed.

The customer or tenant identity must be validated independently of the idempotency key.

A valid key must never allow a different customer to retrieve another customer's payment result.

### 12.2 Key Confidentiality

Idempotency keys should be treated as operational identifiers.

They should not contain:

- Card numbers.
- Bank account numbers.
- Passwords.
- Authentication tokens.
- Personal identification numbers.

Raw keys should not appear in application logs unnecessarily.

The Python implementation records a shortened hash of the key in its event stream.

### 12.3 Request Fingerprint Integrity

The fingerprint must cover every business attribute that can materially change the operation.

An incomplete fingerprint may incorrectly classify two different payment requests as equivalent.

Canonicalization rules should be stable and consistently implemented across services.

### 12.4 Payment Data Protection

Payment methods should be represented through provider-managed tokens.

The database stores token references rather than raw card credentials.

Sensitive data should be protected through access controls, encryption, restricted logging and appropriate retention policies.

### 12.5 Abuse Prevention

Additional production controls should include:

- Authentication rate limits.
- Customer-level request limits.
- Maximum request body sizes.
- Key length restrictions.
- Duplicate request monitoring.
- Audit retention.
- Restricted database permissions.
- Detection of repeated fingerprint conflicts.

## 13. Failure Modes and Mitigation

| Failure condition | Risk | Appropriate handling |
|---|---|---|
| Client retries after timeout | Duplicate payment | Reuse original key |
| Same key, different amount | Incorrect operation reuse | Reject with conflict |
| Concurrent duplicate requests | Multiple payment creation | Atomic key reservation |
| Database transaction rollback | Inconsistent local state | Roll back related records together |
| Gateway declines payment | Incorrect success reporting | Persist confirmed failure |
| Gateway response is lost | Unknown payment outcome | Reconcile provider |
| Application restart | Lost in-memory registry | Use persistent database records |
| Key expires during processing | Duplicate execution risk | Preserve unresolved records |
| Provider reference collision | Incorrect transaction association | Enforce unique provider references |
| Client generates a new key on every retry | Duplicate logical operations | Preserve key across retries |

## 14. Performance and Scalability

### 14.1 Lookup Complexity

The Python dictionary, JavaScript Map, C++ unordered_map and Java ConcurrentHashMap provide average constant-time lookup.

The PostgreSQL implementation uses a unique B-tree index for idempotency key retrieval.

These structures reduce the cost of checking whether an operation already exists.

### 14.2 Database Indexing

The PostgreSQL script indexes:

- Idempotency keys.
- Customer payment history.
- Payment status and creation time.
- Gateway attempt history.
- Expiration timestamps.
- Operational events.

The indexes support common retrieval and monitoring patterns.

Excessive indexing increases storage requirements and write costs. Indexes should be evaluated against actual query plans and workload measurements.

### 14.3 High-Volume Processing

For large-scale payment systems:

- Partition historical operational data when justified.
- Keep active idempotency records accessible.
- Use bounded cleanup batches.
- Avoid unnecessarily long database transactions.
- Use provider-supported transaction lookup.
- Separate payment processing from reporting workloads.
- Monitor lock contention.
- Track unresolved transaction age.
- Use durable messaging for asynchronous processing.

The idempotency registry must remain available throughout the supported retry window.

## 15. Practical API Response Design

A payment endpoint can use the following response conventions.

| Situation | HTTP status | Interpretation |
|---|---:|---|
| New successful payment | 200 or 201 | Payment completed |
| Completed duplicate request | Original status | Original result returned |
| Request conflict | 409 | Same key, different payload |
| Invalid input | 400 | Request validation failed |
| Unauthenticated caller | 401 | Authentication required |
| Unauthorized caller | 403 | Access denied |
| Processing or unknown outcome | 202 | Operation requires follow-up |
| Confirmed payment decline | 402 or documented business error | Payment not approved |
| Unavailable service | 503 | Temporary service failure |

The exact response policy should be documented for API clients.

A duplicate success response should preserve the original payment identifier and business outcome.

A 202 response should provide an operation identifier or status resource that allows the client to retrieve the result without creating a new payment.

## 17. Testing and Verification

The implementations provide executable checks for their central invariants.

Important verification conditions include:

1. A new key creates one payment.
2. A retry with the same payload returns the original payment identifier.
3. A different payload using the same key is rejected.
4. Concurrent duplicate requests do not create separate payments.
5. A completed failure is handled according to the configured failure-caching policy.
6. An unresolved provider result is not automatically treated as a confirmed failure.
7. An expired unresolved record is retained for reconciliation.
8. Invalid payment amounts are rejected.
9. Invalid currency values are rejected.
10. Invalid payment state transitions are prevented.

For production systems, integration tests must also simulate:

- Multiple application instances.
- Database transaction rollback.
- Concurrent inserts with the same key.
- Provider response loss.
- Provider lookup failures.
- Application restarts.
- Delayed provider callbacks.
- Cleanup racing with active requests.
- Duplicate webhook delivery.

The strongest tests verify the actual number of provider-side charges, not merely the number of HTTP responses.

## 18. Important Design Limitations

The five implementations are complementary reference models rather than interchangeable production payment platforms.

The Python, JavaScript, C++17 and Java 17 implementations use in-memory registries.

Their records do not survive process restarts and are not shared between application instances.

The C++17 fingerprint is deliberately non-cryptographic and must be replaced before production use.

The JavaScript Promise coordinates concurrent calls only within one process.

The Java locking model does not replace database-level distributed synchronization.

The PostgreSQL implementation provides persistent coordination, but external provider execution still requires a carefully designed application transaction boundary.

A production architecture should combine:

- Durable idempotency records.
- Atomic database reservations.
- Request fingerprint validation.
- Provider-side idempotency support where available.
- Durable operation identifiers.
- Explicit UNKNOWN states.
- Provider reconciliation.
- Controlled key retention.
- Security and operational monitoring.

The central engineering requirement is that a retry must refer to the original logical operation rather than silently create another payment.
